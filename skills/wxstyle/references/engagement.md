# 结尾问题：让读者愿意留言

读者留言不是因为写了“欢迎评论区聊聊”，而是因为留言成本低、说出来有回报。所以结尾不放口号，放一个具体的问题。问题由作者选定，作者的号召式结尾习惯（画像里写明的）可以保留，但问题本身要过下面的标准。

## 一个好问题的标准

1. **好回答**：读者用一两句话、凭自己的经历就能答，不用先想清楚一个立场。
2. **自己的经历**：问的是“你遇到过什么”“你怎么处理的”，不是“你觉得会怎样”。
3. **不问表态**：不问“你支持还是反对”“你怎么看”“AI 会不会取代你”，这类问题读者要么没想法，要么怕说错。
4. **和本文有关**：从文章里没验证的地方、作者想知道的地方长出来，读者一看就知道为什么问他。
5. **只问一个**：两三个问题读者一个也不答。

| | 例子 | 为什么 |
|---|---|---|
| 差： | 你怎么看 AI 判断这件事？欢迎在评论区聊聊。 | 要表态，没有具体对象 |
| 差： | 你会用吗？ | 是非题，一个字就答完，不产生内容 |
| 好： | 你工作里有没有那种“拿不准就该找人”的判断？说一件就行。 | 用自己的经历回答，一句话能写完 |
| 好： | 文档没写这一步要多久，你要是试过，卡在哪一步？ | 邀请读者补文章没有的部分，用文档没写代替“我没试过” |
| 好： | 你们团队的工单是怎么分的？按人还是按类型？ | 具体、好答、对作者有用 |

## 怎么从文章里找问题

- **文档没说清的地方**：“文档没写”“官方没给数据”，就问用过的读者他们遇到的是什么情况。
- **文中的分界点**：比如“低把握转给人”，就问读者自己那里的那条线画在哪。
- **读者最可能有的处境**：写给不懂代码的职场人，就问他们工作里对应的具体场景。
- 不要为了问而问：文章没有留出自然的问题时，不加结尾问题，比硬凑好。

## 边界

- **不替作者承诺**：不写“我挑几个留言，下一篇拆给你们看”“我会继续跟进”这类作者没说过的后续行动（`claim_check` 会标出 `author_promise`）。作者愿意，才把承诺写进问题候选里并注明是作者的决定。
- **不编留言**：不写“不少读者留言说……”，除非作者提供了真实留言。
- **回复留言是作者的事**：最初几条留言有没有回复，对后面读者是否愿意留言影响很大，但只能由作者做。交付时在回复末尾提醒一句，不在正文里替作者答应。
- **作者的号召习惯**：画像 `ending.style` 是号召式时，“点个关注”这类结尾可以保留，用 `ai_tell_check.py --allow engagement_bait` 放行，并在 review.md 写明。

## 交付时怎么写

review.md 的“留言问题”里给 2—3 个候选，每个写一句“它从文章哪里来”，标出推荐的一个；正文只放选中的一个。作者没选时用推荐的，并在回复里说明可以换。
