# 社区讨论作为素材

**验证次数：0**——写得很细，但目前没有一篇真正交付的文章用上过社区评论（linux.do 被墙、评论没拿到；RAG 那篇也没用到）。这是为一个还没真正发生过的场景做的准备，下次用到时先看这套流程是否还适用，不要在没有新证据前继续扩展它。

官方文档说明"产品能做什么"，社区里的真实测试说明"到手上是什么样"。前者是主张，后者是别人的使用记录，两样放在一起，文章才既有依据又有真实感。`wxstyle-write` 收集素材时，对AI产品、工具和模型类选题，先看有没有值得用的社区讨论。

## 素材来源分几类

| 来源 | 适合拿来说明什么 | 要小心什么 |
|---|---|---|
| 官方文章、文档、更新日志 | 产品身份、功能、价格、官方承认的限制 | 都是官方主张，数字多是自测 |
| 社区论坛（如 linux.do、V2EX、Hacker News、Reddit） | 真实测试、踩坑、和官方说法对不对得上 | 单条只是个人自述；热度不等于真实；可能是营销号 |
| 开发者教程和博客 | 上手步骤、作者自述的数字和案例 | 作者自述，多数没有独立复现 |
| 第三方评测、独立复现 | 验证官方的数字 | 要看测试条件和口径是否可比 |

## 什么样的社区内容值得用

优先选能回答"他到底测了什么、怎么测的"的内容：

1. **问题清楚**：贴出了输入的问题或任务原文，别人能照着再做一遍。
2. **条件交代**：模型或版本、设置、时间、环境。没有条件的数字不可比。
3. **结果具体**：有输出、数字，或者明确的失败情况，不是"太强了""不行"。
4. **能和官方对照**：要么印证官方的说法，要么指出对不上的地方，两种都有价值。
5. **有来源可回溯**：能给出原帖和楼层的链接、用户名和发帖时间。
6. **看回复上下文**：读原帖和相关回复，别只截一条。看有没有人复现、纠正或补充。

不用或降级使用：只有情绪的评论、广告和引流、二手转述、没有测试条件的"跑分"、无法核实来源的截图。

## 怎么整合进文章

- 单独成一节，如"社区里的真实测试"，放在官方数字之后，让读者先看到官方说法，再看到别人的验证。
- 每条按"测试的问题 → 结果 → 条件与局限"写，可以做成一张小表：测试者、问题、结果、条件、来源。
- 短引原话，其余意译并标"意译"；英文评论附中文意译。引文只留能说明问题的一两句，不整段搬。
- 标明是自述：写"某用户称""他说自己在……上测过"，不写成"测试表明"。没有互动数据不称"热门""高赞"，几条评论不代表共识。
- 和官方说法冲突时，两边都写出来并说明条件不同，不替其中一方下结论。
- 主张表里类别记"社区自述"，来源写到楼层链接，核对日期写读到的日期，限制写"单人、未复现"。
- 只用公开内容；不放头像、联系方式等个人信息；用户名用公开昵称，或按需要匿名化。

## 拿不到内容时

- 有些社区会拦截自动抓取（linux.do 在我试的时候返回403，网页版停在验证页）。**不要绕过验证码或人机校验**。
- 请作者把帖子和楼层的文字直接粘贴过来，附上链接、用户名、发帖时间；作者用自己的浏览器复制，最可靠。
- 没有原文就不写这条评论的具体内容，不凭印象或摘要补写。也不要写"社区反馈良好"这类没有依据的概括。

## 与其他规则的关系

- 评论选择的细则见 [visual-evidence.md](visual-evidence.md) 的"评论选择"；截图评论时保留上下文，核对使用条件。
