# 改稿复核：容易改坏的地方

`wxstyle-write` 第5步、第7步（独立审查，见第八节）和 `wxstyle-review` 使用。来自一篇资料介绍文章连续几轮修订暴露的问题：压缩篇幅时删掉了核心内容，改标签时归因丢了，补案例时缺参照。每次改稿后，用本清单回头看一遍，不只看"新改的地方"。事实性主张该怎么写，权威定义在 SKILL.md「证据规则」，本文只查"改动有没有把已经写对的东西改坏"，不重新定义规则。

## 一、改稿回归（压缩、拆段、换结构之后必查）

| 检查 | 常见失误 |
|---|---|
| 标题和小标题承诺的内容还在吗？ | 为了压篇幅删掉"新在哪""为什么"这类核心机制，只剩一句泛泛的话 |
| 例子是否演示完整链路：输入、输出、读者拿它做什么？ | 只展示"问了什么"，没展示"答案怎么用"，例子成了摆设 |
| 每处转述的归因还在吗（官方、教程、转述、自述、我的推测）？ | 重写时把"据教程"删了，社区说法读起来像官方事实；也别把"只有""所有"这类绝对词带进去 |
| 列表引语说的类别，与每一条的性质一致吗？ | 把官方的强项主张放进"三条限制"里，随后又要靠一句"注意最后一条"纠错 |
| 改写涉及官方编号列表（局限、场景、对比维度）时，写“共X条”前先点数，逐条比对官方原始条目数，不能只对"归成几类"这句话本身、或者对上一版的文字 | 重写时把上一版已经补上的条目又弄丢了；每次改完都重新点数，不信任“上次核过” |
| 小标题超出内容了吗？ | "谁在用"底下其实是"没有客户，只有演示"，标题在暗示不存在的事 |
| 改稿后重跑机械检查，同步文件哈希，重写受影响的主张表 | 只改正文不重审，delivery 里哈希对不上 |
| 用了外部工具（ChatGPT等）润色或重写全文时，逐张核对图片链接还是不是自己的素材 | 外部工具改写时会把图片链接换成它自己训练/示例数据里眼熟的一个地址，看着像模像样，其实指向不相关的网站；用 delivery.json 里登记的 source_url 逐个核对，不认得的链接不能留 |

- **自我保留声明的范围**：引用官方的自我保留声明（"这个数字可能有偏差""还不成熟"）时，要看清它在原文里针对文中的哪些具体主张，不能凭印象套到别的主张上；一处保留只能说明它挨着的那几条，不能替全文的说法背书或加重。

## 二、开头与推进

- **选题和角度写"这对读者的工作意味着什么"，不是产品功能清单。** 同样一个发布，"新出了哪些能力"和"这会怎么改变程序员/运营/设计师干活的方式"，读者认领的是后者——先想清楚这次内容跟本文读者(见己方画像 positioning)的哪类具体工作有关，再决定按哪个功能切入，没关系的功能可以少写或不写。
- **开头可以先说出读者正在经历的真实处境，再引出话题。** 比如"收藏夹里存的 AI 工具越来越多，真正用进工作流的没几个"——这类开场利用的是读者本来就有的感受，不是编出来的焦虑，更不能是本节后面明确禁止的恐吓话术（"不学 AI 就会被淘汰"）；判断标准是这句话是不是本来就该是读者会点头认同的真实状态，不是为了制造紧迫感现造一个。
- **先让读者看懂"这是什么、能干什么"，证据强度、保留和局限放在理解打好基础之后再展开。** 核实和写作时是先查到什么就先记什么，正文的顺序不能照抄这个顺序：证据、局限、保留这些内容全篇累加起来往往和"是什么"一样多甚至更多，全堆在前面，读者还没搞懂产品长什么样就先看到一堆保留，反而记不住产品是什么。一篇资料介绍读完，读者要能一句话说出"这是个做什么的东西"，这句话不该需要拼凑全文才拼得出来。
- 举例优先用最贴近读者处境、一眼能看懂"给了什么、它答了什么"的例子；抽象或需要额外解释背景的演示（技术圈的梗、内部工程细节）放到后面当补充证据，不要用来开头。
- 开头不要"先承诺、再撤回"。要给读者结论就一次说完整，推测明确标成推测，同时说出证据缺口。
- 不写“我没用过”式的免责声明，用来源归属的写法（“官方文档写的是……”），见 SKILL.md「证据规则」。资料来源在读者需要判断可信度的地方交代，不要插在钩子中间。
- 一节里"重复同一事实"不超过两次；同一归因句（如"官方文章没有客户案例"）全文不超过两次。运行 check_layout.py 看 repeated_phrase 提示。

### 两条落到动作上的原则

- **结尾前要有一句收束判断**（峰终效应：结尾决定读者记住什么）：结尾问题之前，先用一句话说清“这篇讲的是什么、作者怎么看”，不能停在互动问题上没有落点。
- **并排的数字，两边锚点都要有来源**（锚定效应）：价格、速度对比表之所以有效，是读者会拿一个数字给另一个定位；编一个数字来定位效果一样强，但那是误导。

**不用的心理技巧**，即使更能拉动点击或转发，也不用，因为要靠误导读者才有效，这和整套证据规则的出发点矛盾：

- 制造虚假的社会认同（“大家都在用”“都在讨论”，没有数据支撑）——claim_check 的 `unsupported_heat`、`unsupported_generalization` 已经在拦这个。
- 用损失厌恶或制造焦虑的话术夸大不用的后果（“不懂这个你就要被淘汰了”）——本质是恐吓，不是给信息。
- 稀缺性话术（“仅限今天”“名额有限”）——公众号文章不是促销页。
- 故意扣留读者需要的信息制造悬念（标题党式的“最后一个原因亮了”）——好奇心要来自内容本身的反差，不是刻意让读者猜。

## 三、读者与术语

- 先确定读者。面向不写代码的人，把术语列一张清单：正文、表头、引语、图注里出现的都算。
- 术语第一次出现就解释，位置要在首次使用之前（表头里的 token 也算首次出现），解释用半句人话，不写词典定义。
- **可以先给一个类比，再给准确说法**：类比能让读者一秒钟抓住大概是怎么回事（比如"RAG 像开卷考试，模型考前先去查资料"），比直接堆术语定义好懂。但类比是简化，不是机制本身：给完类比之后，还要接一两句准确说明它简化或者漏掉了什么，不能让类比替代解释，读者照字面理解类比会理解错的地方要点出来。
- 例子取自作者能核实的范围。作者自己编的例子标明"我编的"，示意图标明"内容为假设，非真实返回"，也不放假的具体数值，用"很高""较高"这类定性词。

## 四、数字与案例

- 自述数字必须有参照：和什么比、是不是同一件事。没有参照的数字读者无法判断，要补参照，补不了就删。
- 两件事不可比时直接说"不能直接比价"，再讲能看出什么。
- 案例写清"用它做了什么"（输入、它做的判断、输出），只写"跑完了一个任务"等于没写。
- **有真实案例材料时，按"遇到问题→原来的办法→引入AI→踩坑→调整→结果"这个顺序写，比罗列参数表更容易读完**——读者记的是一件事的经过，不是一堆并列的功能点。这个结构只能用在真实案例上（作者自己的经历，或者有据可查的社区案例）：**没有真实材料时，不为了叙事效果去给案例编一个人、编一段经过**，改用"假设案例"并按规则标明"假设""我编的"，宁可写得没那么有画面感，也不能编一个像真事的过程。
- 引用外部教程里的案例，要回到原文核对细节，不凭上一轮印象或摘要转述。

## 五、标题与时效

- 标题包含产品名或搜索词，读者才搜得到；不写太空的"有个AI模型"。
- 相对时间词（本周、今天、最近）换成具体日期，或确认发布日期后保留。check_layout.py 会提示 relative_time。

## 六、视觉与版式

- 每张图要说清"支撑哪段、增加什么信息"。首屏之后的第一个视觉停顿，优先用能帮读者理解例子的图，而不是产品页面截图。
- 英文密集截图对中文读者信息量很低。数据改成中文文字表格并标明来源，只在需要证明"官方原话"时才保留原图。
- 外观相同的元素不要承载性质不同的内容。比如官方原话和虚构的示例消息，都用引用块，读者会混淆；虚构内容放进示意图或明确标注。
- 元素用量由画像和内容决定：引用、列表、表格连续出现三个以上会显得碎；加粗全文2—3处足够，统一用在同一层级，不要三点里只有一点加粗。
- 中文正文统一弯引号“ ”。check_layout.py 会提示 straight_quote。
- 封面单独考虑（公众号封面图约 900×383），不放进正文；不承载未核实的事实，有来源的事实能不能上封面按[标题与封面](title-and-cover.md)。

## 七、声音

- 没有实测就不冒充实测，也不自我免责，但可以有立场：用"我的判断是……，依据是……"标明，并把依据摆出来。
- 收尾不写整齐的口号式对句，除非对标画像本来就这样收尾。
- 语气按己方画像，别让全篇只剩"官方称……官方说……"的转述腔。以"官方"开头的段落过多，说明缺少作者自己的句子。

## 八、独立审查（SKILL.md 写作流程第 7 步）

**验证次数：1**（2026-10-09，在一篇已知有漏洞的稿子上试过一次，查出了写稿人自评漏掉的限定，起因见 CHANGELOG 1.16.0）。下次用到时先看这套清单是否还适用，不要在没有新证据前继续扩展它。

**交给谁**：一个没看过写稿过程的子代理。只给它 article.md、sources.md（链接清单）和推荐标题（正文里不写标题，审查者要靠它判断标题兑现没有），不给 review.md 的自评和主张表，否则它会沿着写稿人的思路读。让它自己打开原文，数字、原话用 curl 等方式拿原始文本，不用网页总结工具的转述。

**给审查者的说明**（可直接用）：

```text
你在审一篇准备发到微信公众号的文章，读者是：[己方画像 positioning]，标题是：[推荐标题]。
只读 article.md 和 sources.md，自己去打开 sources.md 里的原文。
1. 事实：正文里每一句事实性说法（数字、日期、谁说了什么、能做什么不能做什么），回原文找出处，连同前后两句一起读。逐条写：正文怎么说、原文怎么说（贴原句）、有没有说满、漏了限定或转折。找不到出处的单独列出。
2. 读者：读完能不能一句话说出“这是什么、对我有什么用”？写出这句话。标题承诺的，正文兑现了没有？
3. 最弱的一处：全文最该删或最该补的一段，说明为什么。
每条问题标“必须改”（事实错误、说满了、标题不兑现）或“建议改”。不要改文件，只出报告。
```

**写稿人怎么处理**：报告原样摘要进 review.md 的“独立审查”一节。“必须改”的先改，改完重跑受影响的机械检查、同步哈希；不同意的写明理由和原文依据。审查者自己也可能读错，回原文核一遍再改，不照单全收。

**成本**：每篇多一次子代理运行。只改了几个字、事实没动的小改稿，可以不重审，在 review.md 写明“改动未涉及事实，沿用上次独立审查”。
