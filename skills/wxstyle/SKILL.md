# wxstyle：公众号写作与交付

学对标账号的解释方法和节奏，守住作者自己的声音：本次要求 > 己方画像 > 对标画像。发布由作者手动完成。`scripts/`、`references/`、`profiles/` 都相对本skill的基准目录（Base directory），不是当前项目目录。

## 规则的适用范围

- **硬边界**：不编造事实、来源或作者经历，不冒用他人身份，不替作者作未授权的许诺；事实与推断、假设要能区分。
- **默认策略**：选题渠道、写作顺序、段落长度、标题与结尾形式，按读者、文章类型和本次要求调整，不以套齐模板为目标。
- **可选技巧**：机制六段结构、互动问题、叙事顺序等，只在能改善理解时使用；不适用就省略或换法。

## 按请求决定做多少

| 用户说的 | 做什么 | 产出 |
|---|---|---|
| `topics` / 今天有什么值得写 / 帮我找选题 | 找选题，见“找选题” | 回复里给3个候选，不建目录 |
| `analyze`（`--self`）/ 分析这几篇 / 学某个号 | 画像 | profiles/ 下的画像 + 摘要 |
| `write` / 写一篇 / 帮我出稿 | 完整写作流程 | 文章目录 |
| `rewrite` / 改这篇稿子 | 改稿：保留作者原有事实和观点，改结构和表达；改完对照原稿，不丢原有的事实、数字、归因。默认忠实润色，不擅自新增例子、角度和论点；用户要求深改、补充解释或加强论证时，允许新增有来源的材料、教学示例和明确标注的推断，不替作者改变立场。重新核对原文时发现原稿漏掉的限定或写错的地方可以补；新增内容在review.md列成“新增”，事实附原文措辞，示例和推断标明性质与依据；改了什么写进review.md | 文章目录 |
| `titles` / 只要标题、摘要、开头 | 只做这一步，给3—5个候选 | 回复里给，不建目录 |
| `prep` / 配图、排版 | 配图与排版 | 更新文章目录 |
| `tietu` / 做成贴图 / 发小绿书 | 贴图，见[标题与封面](references/title-and-cover.md)的“贴图” | 文章目录里的 tietu.md |
| `visual` / 分析这些贴图截图 | 贴图视觉画像，同上 | profiles/visual_{主题}.md |
| `review` / 看看能不能发 | 审核，含“独立审查” | review.md |
| `list` / 列出画像 | 列画像 | 回复里给摘要 |
| `log` / 这篇发了 / 阅读多少 / 记一下数据 | 在己方画像把这篇标为已发布、填发布日期；作者给的数记进 performance_log，没给的留空；数据里出现、但 recent_topics 没有的已发布题目，一并追加进 recent_topics（不是本 skill 写的文章也要加，否则找选题会重复推荐） | 回复里说明记了什么 |

`/wxstyle` 后面第一个词是上表的子命令就按那一行做，拼错一两个字母（如 topocs）也按最接近的认；旧写法 `wxstyle-write` 这类同样认；不是子命令就按自然语言判断。多个请求按依赖关系组织，用户明确指定的顺序优先。用户中途改要求，以最新要求为准，已做且仍有效的部分不重做。

## 输入

- **必须**：选题或已有稿，至少一样。用户要找选题，就按“找选题”去找；只说写一篇、又没给题目，先问。第一次找选题且定位不明时，问账号写给谁看。作者立场、改稿幅度或关键实测条件不清且会影响正文时，也可提前问；能合理推定的小事说明假设后继续，不为可自行获取的资料提问。
- **可选**：对标账号和样本、作者实测记录、截图、评论、字数、发布日期、图片要求。
- **自己去取，不要问用户**：官方文档、博客、价格页；profiles/ 里的画像和 `self_only_fields.article_history`；已有文章目录；能访问的社区讨论。
- **不能假设**：作者用过或测过；评论、点赞、热度、阅读数；没有样本时的对标风格；未当天核对的价格、版本、可用范围；作者没说过的立场。缺这些就按“证据规则”标出来，继续写。

## 找选题

仅找选题时读[选题流程](references/topic-selection.md)，按新闻或常青请求选渠道，先看读者价值，再核实来源和信息差；回复默认推荐3个，不建文章目录。

## 按需加载与任务边界

只读当前任务需要的参考文档：选题读选题流程，画像读画像规则，标题或封面读标题与封面，配图排版读视觉与排版规则，完整成稿读素材与交付和审核模板。机制结构、留言问题和点击测试只在适用时读。

只改一句、局部段落、只要标题或讨论角度时，直接给所需内容；不自动建文章目录、做封面、写回画像或启动整稿独立审查。用户要求修改已有文件时，局部修改保存回原文件；只要建议或改后段落时直接回复。修改文件后，复核受影响的事实与归因；若已有 delivery.json，则同步受影响的审核状态与哈希，不能只改哈希冒充已审。

完整写作或整稿改写按下面流程交付；没有自然留言问题时省略该项，已有可用封面不重复生成。步骤可复用已有有效结果，不为满足顺序重复取资料或重做产物。

## 写作流程

1. **定范围**。判断类型：资料介绍、教程、实测、观点；如果是讲清一个AI机制怎么运作（RAG、上下文管理这类），可参考[机制讲解结构](references/explainer-structure.md)，这不是强制模板，只在类型确实是机制讲解时用。对照己方画像的 positioning 看能否帮助读者行动、理解或决策；和定位冲突时（例如定位写给不懂代码的人，选题只能通过API用），先简短说明冲突；用户已明确角度时保留该角度，不自行换题或改承诺。用户未限定角度时，可给两三个调整角度，选一个符合原请求的角度继续写。
2. **取资料**，按下面的“工具策略”。把关键主张记进 review.md 的主张表：主张 | 类别 | 来源 | 原文措辞 | 核对日期 | 限制。原文措辞贴原句（英文贴英文），没读到原文就写“没读到”。AI产品、工具类选题可以找有测试条件的社区讨论，选法见[配图规则](references/visual-evidence.md)的“评论选择”。
3. **搭结构**。3—5个标题候选和摘要，再给封面方案和可直接交给 ChatGPT 等生图工具的封面提示词，写法、尺寸和提示词写法见[标题与封面](references/title-and-cover.md)；标题默认含产品名或搜索词；发布日期未定时避免“本周”“今天”，日期确定且与选题有关时可保留；按证据选开头，避开 article_history 里最近用过的hook。
4. **写正文**。默认读画像JSON；指定了对标号、或画像不足以判断风格时，可以再读 `_raw` 里 2—3 篇原文找节奏和语气（验证次数：0），只学节奏、结构和讲法，不照搬句子、整篇骨架或对方的自称、署名、口头禅，写完必须跑 `similarity_check.py`；没有对标画像就用通用结构，在review.md里写明，不说学会了某个号的风格。段落按阅读节奏和论证完整性组织，默认一段一个意思；没证据的地方缩小结论，不用金句填。
   - 写完正文再定结尾问题：从文章里找2—3个适合读者回答的具体问题（经历或有依据的判断），放review.md的“留言问题”，正文只放选中的一个；文章没有留出自然的问题就不加。默认问具体经历；观点稿也可问有具体对象和理由的判断题，避免空泛表态，不替作者承诺挑留言或写下一篇。标准和例子见[结尾问题](references/engagement.md)。
5. **自查改一轮**。用[审核模板](references/review-checklist-template.md)的质量六项找弱项先改；六项只用来改稿，不在 review.md 给自己打分，打分交给第7步的审查者（写稿人给自己打分会偏高）。压缩、拆段、换结构后按[改稿复核](references/editorial-checks.md)回查核心机制、例子链路、归因。再对照主张表的原文措辞逐句查四类：限定词有没有丢（发布时、符合条件的、默认、可能）；术语译得对不对；“都”“全部”“下面几条”这类范围说法有没有超出来源；有没有只在网页总结里出现、原文没核到的说法。摘引文时把原文前后两句也读完，紧跟着的限定或转折（如“想要完成真正支付，还需要后续逐步放开权限”）要一起收进主张表。
6. **机械检查**，命令和读法见[检查脚本说明](references/checks.md)：`ai_tell_check.py`、`similarity_check.py`（有对标原文时）、`claim_check.py --review review.md`、`check_layout.py`。命中逐条复核后再决定改不改：error 必须改；warn 和弱信号只是提示，按读感判断，为了过检查改得更难读的不改，在 review.md 写一句理由。画像里写明的写作习惯（如号召式结尾）会被当成套路命中，用 `ai_tell_check.py --allow 类别` 放行，并在review.md写明放行了什么。
7. **独立审查**：写稿的人自评看不出自己漏了什么。交付前交给一个没看过写稿过程的子代理，只给 article.md、sources.md 和推荐标题，按[改稿复核](references/editorial-checks.md)的“八、独立审查”查；结果记进 review.md，必须改的先改，再重跑受影响的检查。处理完把 delivery.json 的 review_status 设为 complete、reviewed_article_sha256 写当前正文哈希。没有子代理工具时，写清“同会话复查，独立性有限”，从原文重新读一遍再查。
8. **交付**，按“输出”。

用户要求提高封面点击或验证吸引力时，读取[封面生成与测试](references/cover-testing.md)，区分设计判断、模拟选择与真实随机实验；没有行为数据不宣称高点击。

画像分析时读[画像规则](references/style-profile-schema.md)的“分析与更新流程”；同一账号更新既有画像，账号名用公众号后台显示的名称，统计和保存后校验按该文档执行。

配图与排版按[配图规则](references/visual-evidence.md)和[排版规则](references/wechat-layout.md)：真实素材优先，没有就标待补，不用无关图或假界面；每张图逐张看实际画面。

## 工具策略

核对数字、限定、版本与价格时读[素材与交付](references/evidence-and-delivery.md)的“工具策略”：原文优先，网页总结只找线索。页面打不开、查不到、来源冲突时标明缺口并缩小结论；脚本未运行不能写通过。已核实资料复用，正文使用的原文保存本地副本。

## 证据规则

正文里每个事实性说法属于下面一类，写法要让读者分得出来：

| 类别 | 正文怎么写 |
|---|---|
| 官方主张 | “官方称”“文档写的是”，附来源 |
| 可核验事实 | 直接写，附来源和核对日期 |
| 社区自述 | 写明是谁、测了什么、条件；单条不代表共识，没数据不写“热门” |
| 作者实测 | 只有作者给了记录才能写“我测了” |
| 推断 | 写清依据（“依据是……”），句式不限；有依据的判断就说得肯定，没依据的才缩小 |
| 假设案例 | 正文里就标“假设”“我编的”，不能只在回复里说 |
| 未知 | 没有数据就删掉这段，或缩小成有来源的说法；正文里不留 `【填：…】`，也不留“待补”“暂无数据”这类空段 |

**归因不用每句都写**：同一段里连续几句来自同一来源，第一句标清楚就够；换了来源、或者从事实转到判断时再标。读者要分清的是“谁说的”，不是每句都看到“据……”“官方称……”，那样全篇会变成转述腔。

**作者建议鼓励写**：读者下一步具体能做什么（比如“先存好户号”“自动扣费先别停”），属于推断，写成“我的建议”就行，不需要来源。实用的建议往往是读者最想转发的部分。

**没有实测时的写法**：默认用来源归属：“官方文档写的是……”“这是官方自测，还没有独立复现”“社区里有人测过（来源、条件）……”。避免重复、无助于判断的自我免责。是否亲测会影响评测、购买建议或操作可靠性时，可以简短说明“我未亲测”，并交代证据范围；不要求删掉必要的透明说明。只有作者给了记录才能写“我测了”。判断写明依据，不冒充作者已经持有的立场。

需要作者补材料时，在回复里一次问完最多3个问题（有没有实际用过、最想拿它试什么、有没有真实评论或截图），是为了让作者补真实材料，不是留空段：作者补了，再加进正文；没补，正文照样完整。

作者没说过的后续行动（“我去测”“下一篇写”），不能替作者向读者许诺，`claim_check` 会标出 `author_promise`；结尾问题涉及承诺时的处理见[结尾问题](references/engagement.md)。

## 输出

以下是完整成稿的交付格式；轻量任务直接回复所需内容，用户明确指定的文件或展示方式优先。

- **文章目录**：用户指定的位置；没指定就放当前项目的 `articles/{日期}-{主题}/`。当前项目就是本skill目录时，改放同级的 `../wxstyle-articles/{日期}-{主题}/`。已有目录沿用。
- **文件**：article.md（正文，不写 `#` 一级标题；先写开头一两段，再进第一个 `##` 小标题）、review.md（标题候选、摘要、主张表、质量六项、检查结果、待办）；有外链时加 sources.md（链接清单）；每篇都有 images/（至少有封面）和 delivery.json（字段见[素材与交付](references/evidence-and-delivery.md)）。
- **封面保底**：作者没提供封面、也没有已生成的图时，用 `make_cover_card.py` 做一张文字卡，存 `images/cover-card.png`，看过裁切预览再交付；文字从推荐标题里提炼，合计不超过10字（英文字母也按字数算），不放未核实的数字。封面不在正文里，不记进 delivery.json 的 assets（那里只记正文配图），路径写在 review.md 的封面方案里。作者要生图且当前有工具时直接生成；只要提示词时交付提示词。10字限制只适用于该文字卡脚本，不限制其他封面方案。
- **写回画像**：交付后在己方画像的 article_history 追加或更新这篇（article_id 用文章目录名、updated_at、hook、status 为 delivered），recent_topics 去重追加选题，保存后跑 `validate_profile.py`；没有己方画像就跳过，在回复里提一句。
- **最终回复要短**，依次写：交付了什么、是正文稿还是图文稿；**推荐标题**（正文不含标题，作者要填在标题栏，直接给出，备选在review.md）；文件路径；作者要处理的待办，按重要性排；最多3个问题。检查只报数量和要处理的项，独立审查报查出几处、改了几处。作者要看正文时才贴，贴的必须和文件一字不差。

## 完成标准

以下用于完整成稿交付；局部任务只检查适用项。事实性主张的唯一权威定义是上面的「证据规则」表，详细交付字段见[素材与交付](references/evidence-and-delivery.md)。

- [ ] 范围符合本次请求，已有且仍有效的图片、事实和观点未被悄悄丢掉。
- [ ] 关键主张有来源或标明推断、假设；正文没有 `【填：…】` 或空段，没有冒充经历或他人身份。
- [ ] 适用的机械检查已跑或注明未运行，命中已复核；排版 error 为0。
- [ ] 独立审查做了（或记录同会话复查的限制），问题有处理结果；审核记录对应当前正文。
- [ ] 文件已保存，封面保底和写回画像按“输出”完成；运行 `check_delivery.py <文章目录> --profile <己方画像>`，无画像时省略参数，warnings 已处理或说明。
- [ ] 最终回复提供推荐标题、路径和有实际影响的待办；未完成素材或审核时准确说明交付状态。
