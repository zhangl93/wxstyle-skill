# 机制讲解类文章的可选结构

**验证次数：1**（2026-09-30，RAG文章，且当时因为账号定位冲突做了角度调整）。这份文档还没经过反复验证，下次用到时先看这套结构是否还适用，不要在没有新证据前继续扩展它。

一套六段顺序，配一句口诀：

> 标题卖问题，开头卖共鸣，中间卖认知，案例卖可信度，结尾卖行动。

① 先说读者正在遇到的问题 → ② 给出反常识或核心判断 → ③ 用一个具体案例解释 → ④ 再解释技术原理 → ⑤ 告诉读者边界 → ⑥ 最后给行动建议。

**用在哪**：讲清一个 AI 机制怎么运作（RAG、context window、tool calling 这类）时可参考的顺序，可按内容调整或省略。①②放在④之前，是先让读者知道“这是什么”，再讲原理（见 editorial-checks.md 第二节）。

**不是所有文章都套用这个结构**。wxstyle 覆盖的文章类型包括资料介绍、教程、实测、观点，其中只有"讲清一个技术机制怎么运作"这一类天然适合这六段；评测一款产品的定价、核对一条官方主张、写一篇选题类观点稿，不需要"反常识判断"或"技术原理"这两拍，硬套反而多余。判断类型仍按 SKILL.md「定范围」，这套结构只在类型确实是机制讲解时参考，不覆盖其余类型。

## 逐段的证据门槛

六段里，②和③最容易在没有真实支撑时诱导写出不准确或编造的内容，用之前要过这两关：

- **② 反常识或核心判断**：只有证据真的支持一个反常识判断时才这样写；**证据只支持一个平常的判断，就直接写平常的判断，不要为了套模板硬拗成反常识**。"真正决定效果的，可能不是模型能力，而是上下文管理"这句话要成立，得有具体依据（官方说明、真实对比、作者的实测发现），不能只是听起来更有洞察力。这里还有一个机械上的坑：反常识判断常见的句式是"不是A，而是B"，`ai_tell_check` 的 `reframe` 会把它列出来（弱信号）。判断有扎实依据就保留，硬凑的反差才改成陈述句。
- **③ 具体案例**：真实案例写明来源和条件；没有真实材料时，可以构造 Prompt、代码或工作流程来解释机制，在正文标明“教学示例，未实测”或“假设案例”。示例输出标明“示意，非真实返回”，假设数字标明“假设数值，非测量结果”，不据此证明产品效果或可用性。不能为了填这一步把构造内容冒充作者经历、真实截图或实测结果；例子无助于理解时省略。
- **④ 技术原理**：术语第一次出现就解释，可以用类比降低门槛，类比之后要接一句准确说明，规则见 editorial-checks.md「读者与术语」。
- **⑤ 边界**：什么情况下有效、什么情况下不适合，对应已经在用的"已知局限""官方自己打的折扣"这类内容，不是新要求。
- **⑥ 行动建议**：只给已经核实过的具体步骤（比如确认过的入口地址、确认过的操作路径）；没核实的步骤写成"以官网当时的说明为准"，不能替读者保证"今天就能用"。

## 和一号一稿的关系

即使用这套结构，开头（①）和收尾（⑥）仍然要按己方画像和 article_history 换着写，不要六篇文章都用一模一样的措辞——结构可以重复，具体怎么说读者的处境、怎么给行动建议，每篇不同。结构本身用了几次之后，也回头看看是不是所有机制讲解类文章都长一个样，长期只用一种结构，读者会觉得"又是这个套路"，那时候要主动换一种顺序。
