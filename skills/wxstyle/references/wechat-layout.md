# 公众号排版规则（Markdown 转公众号）

`wxstyle-publish-prep` 输出的 Markdown 按本文写，用 Markdown 转公众号排版工具转换后手动粘贴到公众号后台。规则来自一份工具示例文档的语法说明，加上实际排版中踩过的坑，二者分别标为「示例」和「经验」；在转换工具里实际试过的标为「实测」并写日期。示例没有说明、也没实测过的行为标为「未验证」，不当成事实写给用户。用户实际使用的工具与示例不同时，先问清或让用户提供其语法说明，再改本文。

**「实测」的有效期**：标了实测的行为，是当时那次打开工具时观察到的结果，不是永久保证。工具会更新界面，标了实测的东西，日期太久或怀疑工具变了，就要重新测一次，不能当成永久有效。

**核对 HTML 时别把内联样式一起去掉**：2026-09-30 第一次测列表时，用 `removeAttribute('style')` 清理过再读 HTML，结果把控制"每项独立一行"的关键样式（`display:block`、`text-indent` 做悬挂缩进）一起删掉了，看起来像是所有列表项挤在一段里，得出了错误的"未能确证"结论。去掉 `removeAttribute('style')` 重新读一遍才看到真实结构：每项是带完整内联样式的 `<span>`，视觉上确实独立一行——这类工具因为微信编辑器会过滤真正的 `<ul><li>`，普遍用这种手法模拟列表。以后核对转换效果，要保留原始内联样式再读，不能简化后再判断。

排版服务于阅读，不追求样式齐全。用哪些元素由画像的 `paragraph_rhythm`、`visual_rhythm`、`layout_details` 和本次内容决定，没有真正并列的内容就不硬做列表，没有原话就不硬做引用。

## 结构

| 规则 | 来源 |
|---|---|
| 正文不写 `#` 一级标题，从 `##` 开始，`###` 为下一级。文章标题填公众号后台标题栏，标题候选（3—5个）和摘要写在 review.md | 示例：示例正文从 `##` 开始 |
| 标题不跳级，不为了排版装饰嵌套多层；一篇1500—2500字通常有3—6个 `##` 就够 | 经验 |
| 小标题写成本节的结论或话题，不写"前言""正文""总结"。小标题不要暗示正文里不存在的东西，如"谁在用"下面其实是"没有客户" | 经验 |
| 封面单独准备（约900×383），不放进正文；不承载未核实的事实，有来源的事实能不能上封面按 title-and-cover.md | 经验 |

## 段落与强调

| 规则 | 来源 |
|---|---|
| 段落之间用空行。单个换行会并入同一段，中文之间还会多出一个空格，所以不要靠单个换行分段 | 示例、实测（2026-09-24） |
| 一段只讲一个意思。默认不超过100字，先看画像的 `avg_paragraph_length`，对标是短段风格就更短 | 经验 |
| 加粗 `**词**`、斜体 `*词*`。加粗只给全文最关键的判断或反常点，数量参考画像 `bold_keyword_freq` | 示例（语法）、经验（用量） |
| 加粗标记紧贴标点时，把标点放到星号外：写 `（2）**颠覆还早**。`，不写 `**（2）颠覆还早。**后文`。quaily.com 在线版两种都能正确加粗，但严格按规范的渲染器会把后一种的星号显示成字符，换工具时容易出错 | 经验、实测（2026-09-24） |
| 加粗在同一层级里统一：三点看法要么都加粗，要么都不加，不要只有一点加粗 | 经验 |
| 中文正文统一用弯引号“ ”，不混用直引号 " | 经验 |
| 相对时间词（本周、今天、最近）换成具体日期，发布日期不确定时更要如此 | 经验 |
| 图注用斜体一行，不再重复 alt 的内容 | 经验 |

## 列表、引用、表格

| 规则 | 来源 |
|---|---|
| 无序列表用 `- `，有序列表用 `1. `。只用于真正并列或有先后的内容（步骤、几条限制），每项一行、句子完整，不把整段拆成碎句 | 示例（语法）、实测（2026-09-30）：转换后每项是带 `display:block` 和悬挂缩进的 `<span>`，不是真的 `<ul><li>`（微信编辑器会把真列表标签过滤掉，这是常见的替代写法），但视觉上每项独立一行、带项目符号，效果正确 |
| 引用 `> ` 用于原话、官方表述的意译、示例消息，作视觉停顿，并写明出处，翻译的要写"意译"。不用引用块装饰作者自己的金句 | 示例（语法）、经验 |
| 表格用标准 `\| 表头 \| ... \|` 加 `\| --- \|` 分隔行。不超过3—4列，单元格写短句，数字原样保留并写明来源和"这是我做的整理"。宽表在手机上难读，宁可拆成两张或改成列表 | 示例（语法）、经验 |
| 一节里引用、列表、表格连着出现三个以上会显得碎，中间放一段正文 | 经验 |
| 外观相同的元素不承载性质不同的内容：官方原话用引用块，作者虚构的示例消息不要也用引用块，放进示意图或写进句子里并标明"我编的" | 经验 |
| 官方表格是英文时，转成中文文字表格并标明"我做的中文整理"，比英文截图更适合手机 | 经验 |

## 链接与来源

| 规则 | 来源 |
|---|---|
| 链接写成 `[文字](网址 "来源名，日期")`，放在首次提到该来源的地方。公众号以外的链接会被转成文末脚注 | 示例 |
| 脚注会自动生成：有标题的链接，脚注写标题；没有标题的，写链接文字。文末自动加一个英文小标题"References"。所以不再单写"资料来源"段，也不放裸网址（正文里不可点击） | 实测（2026-09-24，quaily.com 在线版） |
| 完整链接、核对日期放在 sources.md，不塞进正文 | 经验 |

## 图片

| 规则 | 来源 |
|---|---|
| 语法 `![alt](url)`。url 可以是图床，也可以先上传微信媒体库再把地址粘回，或在公众号后台直接插图 | 示例、实测（2026-09-30，alt 正确保留） |
| 本地路径（`images/xx.png`）只用于预览，记为待办：发布时需在后台插入或换成 URL | 经验 |
| alt 简短说明图里是什么；图注写看点和来源；英文截图另附标明"意译"的中文解读 | 经验，配合 visual-evidence.md |
| 图片数量由内容需要决定，不为凑密度加装饰图。首屏不用大而无信息的图 | 经验，配合 visual-evidence.md |

## 代码

| 规则 | 来源 |
|---|---|
| 代码块用三个反引号并标注语言，如 ```` ```python ````，可使用微信官方高亮配色。粘贴到公众号后需用鼠标点一下代码块才会完成高亮，交付时提醒用户 | 示例、实测（2026-09-30，转成了带行号的代码块结构，语言标注被保留） |
| 行内代码用单个反引号 | 示例、实测（2026-09-30，`<code>` 正确生成） |
| 面向不写代码的读者，默认不放代码块，把要点写成文字或步骤 | 经验 |

## 需要避开的语法

| 规则 | 来源 |
|---|---|
| 注音语法：`汉字【读音】`、`汉字{读音}` 在示例里会被转成注音；quaily.com 在线版实测不转换、原样显示。两种情况都不好看，正文里汉字后面不要紧跟 `【…】` 或 `{…}`，补充说明用（）或「」 | 示例、实测（2026-09-24） |
| 正文里不留占位符 `【填：…】`，没有数据的部分整段删掉；`check_layout.py` 把它当 error | 经验 |
| 分隔线 `---` 会转成 `<hr>`，但没有内联样式，预览里高度为0，粘贴到公众号后多半看不见或只剩默认细线。不用它分节，用 `##` 小标题 | 实测（2026-09-24，quaily.com 在线版） |
| 不用 HTML 标签，不用引用式图片或链接（脚本和转换工具可能不处理） | 经验 |

## 检查

```text
python scripts/check_layout.py --file <article.md>
```

除排版语法外，脚本还会提示直引号（straight_quote）、相对时间词（relative_time）、重复短语（repeated_phrase）。内容层面的复核见 [改稿复核](editorial-checks.md)。

`error` 是会导致渲染出错的写法，必须改；`warn` 需要人判断；`pending` 是发布前要处理的事项（占位符、本地图片）。脚本只检查语法层面，零 error 不代表版式好看，仍要手机预览确认：图片文字是否可读、表格是否被截断、引用和列表是否碎。
