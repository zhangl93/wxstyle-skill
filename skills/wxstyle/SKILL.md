# wxstyle：公众号写作与交付

学对标账号的解释方法和节奏，守住作者自己的声音：本次要求 > 己方画像 > 对标画像。发布由作者手动完成。`scripts/`、`references/`、`profiles/` 都相对本skill的基准目录（Base directory），不是当前项目目录。

## 按请求决定做多少

| 用户说的 | 做什么 | 产出 |
|---|---|---|
| 今天有什么值得写 / 帮我找选题 / wxstyle-topics | 找选题，见“找选题” | 回复里给3—5个候选，不建目录 |
| 分析这几篇 / 学某个号 / wxstyle-analyze（--self） | 画像 | profiles/ 下的画像 + 摘要 |
| 写一篇 / 帮我出稿 / wxstyle-write | 完整写作流程 | 文章目录 |
| 改这篇稿子 | 改稿：保留作者原有事实和观点，改结构和表达；改完对照原稿，不新增原稿没有的事实、数字、归因，也不丢原有的；改了什么写进review.md | 文章目录 |
| 只要标题、摘要、开头 | 只做这一步，给3—5个候选 | 回复里给，不建目录 |
| 配图、排版 / wxstyle-publish-prep | 配图与排版 | 更新文章目录 |
| 看看能不能发 / wxstyle-review | 审核 | review.md |
| wxstyle-list | 列画像 | 回复里给摘要 |
| 这篇发了 / 阅读多少 / 记一下数据 | 在己方画像把这篇标为已发布、填发布日期；作者给的数记进 performance_log，没给的留空 | 回复里说明记了什么 |

多个请求按上表顺序做。用户中途改要求，以最新要求为准，已做且仍有效的部分不重做。

## 输入

- **必须**：选题或已有稿，至少一样。用户要找选题，就按“找选题”去找；只说写一篇、又没给题目，先问。需要先问再动手的只有这种情况，以及第一次找选题时问账号写给谁看。
- **可选**：对标账号和样本、作者实测记录、截图、评论、字数、发布日期、图片要求。
- **自己去取，不要问用户**：官方文档、博客、价格页；profiles/ 里的画像和 `self_only_fields.article_history`；已有文章目录；能访问的社区讨论。
- **不能假设**：作者用过或测过；评论、点赞、热度、阅读数；没有样本时的对标风格；未当天核对的价格、版本、可用范围；作者没说过的立场。缺这些就按“证据规则”标出来，继续写。

## 找选题

验证次数：1.13.0 改规则前用过4次（2026-10-04至10-09，都没有阅读数据），新规则（候选只从粗筛来）0次。攒够3篇有阅读数据的，再判断这套标准要不要扩展。

1. **粗筛**：候选只从这一步来。搜最近1—3天的资讯，中英文都搜，先只看标题。先去读者直接用的产品的官方更新日志、官方博客找（按 positioning 定：写给普通职场人，就看 ChatGPT、Claude、豆包、Kimi、通义、元宝，以及办公软件里的 AI 功能），再补一两个具名科技媒体；国内产品多数没有公开更新日志，找不到就直接用具名科技媒体（如 IT之家），在回复里写明看了哪些来源、哪些没读到。“AI news this week”这类泛搜只用来找链接。
   - **定位筛选**：把 positioning 写成一个能直接回答的问题，答不上“能”的不进候选。例：写给不懂代码的人，就问“读者不写代码，今天能不能在网页或 App 里用上”。只能通过 API 用的，除非值得写，否则不收；收了就标“需要换角度”。
   - 旧消息临近截止日（如几个月前的下线通知，数据几天后删除）可以进候选，但要标明“旧通知，新的是截止日”，写出截止日期，不当成新消息。
   - 去掉和 recent_topics、已有文章目录重复的。没有己方画像时，问一次账号写给谁看，建 bootstrap 画像 `profiles/self_{账号名}.json`（只填 `self_only_fields.positioning` 和 recent_topics，sample_count 为0），保存后跑 `validate_profile.py`。
2. **标热度**（可选，验证次数：0）：只给粗筛留下的候选查热度，可以跑 `hot_list.py` 看有没有上百度热搜。**热搜不新增候选**：大众热搜里 AI 条目少，命中的多是 AI 只当背景的社会新闻或开发者向的消息。只在热搜上、粗筛里没有的条目，最多在回复末尾一句带过，并说明离定位远在哪。读不到就写“热度数据没取到”。微博、知乎等要登录或验证的热榜不用，不绕过。
3. **细查前3个**：读一手原文，再对照搜到的二手摘要和报道。
4. **写信息差**：一手原文比二手摘要更准或更全的地方，写成一句并附原文链接，比如摘要漏了适用范围、给的数字找不到出处。找不到就写“无明显信息差”，不凑。只能和搜得到的报道比，比不了其他公众号，不写“别人都没写”。
5. **原文打不开**：标“原文没读到”，排到后面，不把转述当原文。
6. **交付**：每个候选写信息差、热度依据、读者看完能做什么决定、作者能不能补实测、核实难度，推荐一个。热度依据三选一：百度热搜排名、热度分和抓取时间；具名媒体列表（不写“N家报道”）；没有热度数据。上了热搜的候选提醒热度可能等不到发布。排序先看读者，再看信息差，热度只在前两项差不多时决定先后。不预测阅读量。作者选定后进入写作流程；发布后作者给了阅读数，记进 `performance_log`。

## 写作流程

1. **定范围**。判断类型：资料介绍、教程、实测、观点；如果是讲清一个AI机制怎么运作（RAG、上下文管理这类），可参考[机制讲解结构](references/explainer-structure.md)，这不是强制模板，只在类型确实是机制讲解时用。对照己方画像的 positioning 看读者能不能直接用；和定位冲突时（例如定位写给不懂代码的人，选题只能通过API用），先在回复开头说明冲突，给两三个调整角度，选一个写；作者坚持就按原题写。
2. **取资料**，按下面的“工具策略”。把关键主张记进 review.md 的主张表：主张 | 类别 | 来源 | 原文措辞 | 核对日期 | 限制。原文措辞贴原句（英文贴英文），没读到原文就写“没读到”。AI产品、工具类选题可以找有测试条件的社区讨论，选法见[配图规则](references/visual-evidence.md)的“评论选择”。
3. **搭结构**。3—5个标题候选和摘要，再给封面方案和可直接交给 ChatGPT 等生图工具的封面提示词，写法、尺寸和限制见[标题与封面](references/title-and-cover.md)；标题含产品名或搜索词，不用“本周”“今天”；按证据选开头，避开 article_history 里最近用过的hook。
   - 结尾问题：给2—3个读者凭自己经历就能答的具体问题候选，放review.md的“留言问题”，正文只放选中的一个；不问表态题，不替作者承诺挑留言或写下一篇。标准和例子见[结尾问题](references/engagement.md)。
4. **写正文**。读画像JSON，不读 `_raw` 原文；没有对标画像就用通用结构，在review.md里写明，不说学会了某个号的风格。短段落，一段一个意思；没证据的地方缩小结论，不用金句填。
5. **自查改一轮**。按[审核模板](references/review-checklist-template.md)的质量六项逐项写正文依据，明显弱项先改。压缩、拆段、换结构后按[改稿复核](references/editorial-checks.md)回查核心机制、例子链路、归因。再对照主张表的原文措辞逐句查四类：限定词有没有丢（发布时、符合条件的、默认、可能）；术语译得对不对；“都”“全部”“下面几条”这类范围说法有没有超出来源；有没有只在网页总结里出现、原文没核到的说法。摘引文时把原文前后两句也读完，紧跟着的限定或转折（如“想要完成真正支付，还需要后续逐步放开权限”）要一起收进主张表。
6. **机械检查**，命令和读法见[检查脚本说明](references/checks.md)：`ai_tell_check.py`、`similarity_check.py`（有对标原文时）、`claim_check.py --review review.md`、`check_layout.py`。命中逐条复核后再决定改不改。画像里写明的写作习惯（如号召式结尾）会被当成套路命中，用 `ai_tell_check.py --allow 类别` 放行，并在review.md写明放行了什么。
7. **交付**，按“输出”。

用户要求提高封面点击或验证吸引力时，读取[封面生成与测试](references/cover-testing.md)，区分设计判断、模拟选择与真实随机实验；没有行为数据不宣称高点击。

画像分析按[画像规则](references/style-profile-schema.md)：先看 profiles/ 里有没有同一账号的画像，有就更新，不新建；账号名用公众号后台显示的名称，栏目或周刊归到所属账号（同一号在不同会话里起了不同文件名，会让样本数和去重对不上）；只分析读到的正文，读不到就说原因，不凭账号名编；图片型文章先逐张转写；数字用 `profile_stats.py` 统计；按来源或内容指纹去重，重复样本不加 sample_count；保存后跑 `validate_profile.py`，用 `render_profile_summary.py` 给用户看摘要。己方没有可靠样本时，用几组同题对比句让作者选，标为 bootstrap。未经作者实质改写的AI稿不算己方样本。

配图与排版按[配图规则](references/visual-evidence.md)和[排版规则](references/wechat-layout.md)：真实素材优先，没有就标待补，不用无关图或假界面；每张图逐张看实际画面。

## 工具策略

- **找事实**：官方原始页 > 官方文档 > 官方博客 > 第三方评测 > 社区。搜索结果摘要、网页总结工具只用来找链接；数字、条数、日期回到原文核对。平台规则和法律结论只引原文和日期，不用传闻。
- **网页抓取工具返回的是总结**：它给的是另一个模型读完页面后的转述，不是原文。数字、限定词（如“发布时”“符合条件的”）、原话，要么让它逐字引用，要么用 curl、pdftotext 拿原始文本核对；只在总结里出现、原文没核到的说法，按“没读到”处理。
- **社区帖子先看发帖人**：官方论坛、社区里的帖子，先确认发帖人是不是官方员工（看有没有员工标识），发在公告版块不等于官方发的。版主或用户转述的官方公告算转引，正文写“社区版主转述”，并尽量找到原文。
- **页面打不开**（403、验证码、要登录）：不绕过验证。先换同一来源的其他页面（文档、更新日志）；仍不行，在待办写明哪个页面没读到，请作者粘贴原文或用自己的浏览器打开。不凭记忆补内容。
- **查不到**：正文写“没有找到公开资料”或删掉这个主张，不编数字补具体性。
- **来源冲突**：两个官方页面不一致，用更新日期新的并注明；官方和社区不一致，两边都写并标类别；用户说的和来源不一致，正文用有来源的说法，回复里指出冲突请作者确认。
- **脚本**：零命中不等于合格，命中也不等于必须删。脚本跑不了（没有Python、报错），写“未运行”和原因，按 checks.md 的清单人工查，不写“通过”。缺对标原文时相似度标“不可检查”。
- 同一会话里已核对过的页面直接复用 sources.md，不重复抓取。

## 证据规则

正文里每个事实性说法属于下面一类，写法要让读者分得出来：

| 类别 | 正文怎么写 |
|---|---|
| 官方主张 | “官方称”“文档写的是”，附来源 |
| 可核验事实 | 直接写，附来源和核对日期 |
| 社区自述 | 写明是谁、测了什么、条件；单条不代表共识，没数据不写“热门” |
| 作者实测 | 只有作者给了记录才能写“我测了” |
| 推断 | “我的判断是”“可能” |
| 假设案例 | 正文里就标“假设”“我编的”，不能只在回复里说 |
| 未知 | 没有数据就删掉这段，或缩小成有来源的说法；正文里不留 `【填：…】`，也不留“待补”“暂无数据”这类空段 |

**没有实测时的写法**：作者写文章，读者就默认作者是有判断的人，所以正文不写“我没用过”“我没试过”“本文没有我自己的实测”，那会自己拆自己的台；也不能编“我测了”。用**来源归属**的写法代替：“官方文档写的是……”“官方称……，这是官方自测，还没有独立复现”“社区里有人测过（来源、条件）……”，判断写成“我的判断是……，依据是……”。这样既不编造，也不显得心虚。作者给了实测记录，才写成实测。

交付后在回复里一次问完最多3个问题（有没有实际用过、最想拿它试什么、有没有真实评论或截图），是为了让作者补真实材料，不是留空段：作者补了，再加进正文；没补，正文照样完整。

作者没说过的后续行动（“我去测”“下一篇写”），不能替作者向读者许诺，`claim_check` 会标出 `author_promise`；结尾问题涉及承诺时的处理见[结尾问题](references/engagement.md)。

## 输出

- **文章目录**：用户指定的位置；没指定就放当前项目的 `articles/{日期}-{主题}/`。当前项目就是本skill目录时，改放同级的 `../wxstyle-articles/{日期}-{主题}/`。已有目录沿用。
- **文件**：article.md（正文，从 `##` 开始，不写 `#` 标题）、review.md（标题候选、摘要、主张表、质量六项、检查结果、待办）；有外链时加 sources.md；有图片或多轮修订时加 images/ 和 delivery.json（字段见[素材与交付](references/evidence-and-delivery.md)）。
- **封面保底**：作者没提供封面、也没有已生成的图时，用 `make_cover_card.py` 做一张文字卡，存 `images/cover-card.png`，看过裁切预览再交付；文字从推荐标题里提炼，合计不超过10字（英文字母也按字数算），不放未核实的数字。封面不在正文里，不记进 delivery.json 的 assets（那里只记正文配图），路径写在 review.md 的封面方案里。作者想要生图封面，照旧给提示词。
- **写回画像**：交付后在己方画像的 article_history 追加或更新这篇（article_id 用文章目录名、updated_at、hook、status 为 delivered），recent_topics 去重追加选题，保存后跑 `validate_profile.py`；没有己方画像就跳过，在回复里提一句。
- **最终回复要短**，依次写：交付了什么、是正文稿还是图文稿；**推荐标题**（正文不含标题，作者要填在标题栏，直接给出，备选在review.md）；文件路径；作者要处理的待办，按重要性排；最多3个问题。检查只报数量和要处理的项。作者要看正文时才贴，贴的必须和文件一字不差。

## 完成标准

事实性主张该怎么写，唯一权威定义是上面的「证据规则」表；下面是交付前最后再扫一遍有没有漏做，不重新定义规则，做不到的写进待办和回复，不能默默跳过：

- [ ] 做了用户这次要的范围，没多也没少（上一轮要过的图片等不能悄悄丢掉）。
- [ ] 正文里的数字、日期、价格、功能都能在主张表里找到来源和核对日期，或已标为未知。
- [ ] 没有无记录的“实测”“我用了”，也没有“我没用过”式的自我免责，用来源归属的写法；假设案例在正文里标明；没有无数据的热度说法、绝对化承诺或误导性标题。
- [ ] 四个检查脚本都跑了（或写明未运行的原因），命中已逐条处理；`check_layout.py` 的 error 为0。
- [ ] 画像里的对标作者自称、署名、口头禅没有进正文。
- [ ] 正文里没有 `【填：…】` 或空段（没有数据的部分已经删掉）；本地图片、没取到的素材在待办里。
- [ ] 文件已保存；有 delivery.json 时哈希对应当前正文。
- [ ] 封面有文字卡保底或作者提供的图；己方画像已写回这篇。这两项用 `check_delivery.py <文章目录> --profile <己方画像>` 查，ready_for_delivery 为 false 时看 warnings。
- [ ] 回复符合“输出”的格式。
